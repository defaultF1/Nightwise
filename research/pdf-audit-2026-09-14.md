# Nightwise versus the supplied roadmap

Audit date: 14 September 2026. Baseline: `C:/Users/LENOVO/Downloads/GPT maps - roadmap.pdf`, all 14 pages inspected. Pages 1 and 13 are section dividers; page 14 is scripting/background research, not additional app deliverables.

Audited source: Git commit `b141e3b5d953b49bbce58b73a5d2d7a0ca0547b1`, with the local Android packaging version change to 2.0.7 / versionCode 33. APK: `output/apk/nightwise-2.0.7.apk`. This is an audit, not an implementation change.

## Verdict

The project implements the core MVP pipeline and exceeds the minimum in product features. It is not evidence of a fully validated or safer routing product. All 12 module categories have implementations, but some results are conditional on provider data, some UI requirements remain incomplete, and the roadmap's real-route acceptance exercise is not documented as complete.

The former statement that live scoring is disabled is obsolete. Current source implements it, user screenshots show live scores, and the service status checked during this audit reports scoring enabled.

## All twelve modules (PDF pages 6–8)

1. Frontend: implemented in React, with browser and native Android maps.
2. Backend: Fastify API, private server credentials, request validation, budget and origin checks.
3. Route fetcher: Google route geometry, duration, distance and steps; car, motorbike and walking supported in requests.
4. Route sampler: implemented at 200 m in live planning, within the PDF's ranges.
5. Places scanner: restaurants, cafes, food/retail categories, fuel, hospitals, hotels, pharmacies, police and transport. Selected categories are not every possible shop type.
6. Deduplicator: unique place IDs, conflict detection, shared query footprints.
7. Activity analyzer: open listings, staffed-business proxies, help points and transport listings. Staff presence is not observed directly.
8. Low-activity detector: implemented; total-distance presentation remains incomplete.
9. Road-type analyzer: OSM tags and route geometry estimate main/internal roads and turn complexity. Unmatched, parallel and grade-separated roads remain uncertain.
10. Scoring: the suggested 25/20/15/15/15/10 weights are present. Missing components are excluded and remaining weights normalized. Walking excludes the driving-oriented road-component bonus.
11. Explanation: implemented with explicit tradeoffs. Not an LLM requirement; deterministic explanation logic is appropriate here.
12. Handoff: implemented with the qualifications above.

Evidence paths: `src/App.tsx`, `src/native.ts`, `src/PointPicker.tsx`, `src/PlaceSearch.tsx`, `server/app.ts`, `server/google.ts`, `server/search.ts`, `server/scan.ts`, `src/domain/activity.ts`, `src/domain/hours.ts`, `src/domain/roads.ts`, `server/roads.ts`, `src/domain/comparison.ts`, `src/JourneySummary.tsx`, `src/ScoreBreakdown.tsx`, `src/domain/handoff.ts`.

## Beyond the basic brief

- Installable Android APK with native maps, permission/settings integration, Back-button handling and keyboard-aware sheets; the PDF primarily describes a web app.
- Both North Bengaluru and Kanpur coverage circles (20 km), with 22 km road extracts. This expands the geography; it does not prove full data coverage.
- Offline AEOS–Manyata tutorial in both directions using bundled street geometry.
- Three themes, animated score rings with reduced-motion support, category-coloured map pins, dedicated hospital markers.
- Searched origin as well as destination, endpoint confirmation, swapping and locally saved places.
- UI choices for car/motorbike/walk and departure up to five hours ahead. Travel-mode propagation itself is already in the PDF; the selectors and scheduled journey handling extend the basic flow.
- Extra-time preference, arrival-time opening-hours evaluation, holiday/weekly/24-hour handling and labelled missing-hours estimates.
- Persistent team-code entry, Redis usage counters, anonymous helpful/not-helpful feedback, bounded five-minute comparison reuse and explicit refresh.
- Automated tests and signature/assets/credential checks for APK packaging.

Caching, main-road analysis, help points, scoring and destination autocomplete are already roadmap requirements, so they should not be counted as wholly extra features.

## Incomplete or not proven

1. Complete the PDF's 10–20 real-route evaluation, covering shortcut/main-road cases, late-night trips and recommendation reasonableness. The PDF says Chennai; later user instructions select North Bengaluru and Kanpur. Treat this as an agreed scope change, not a requirement to add Chennai now. Ground checks and reel work were previously deferred and are not missing code.
2. Prepare and validate 2–3 dependable live demo journeys. The tutorial and preset do not prove the same live data quality.
3. Expose total low-activity distance clearly, alongside longest observed stretch and unknown sections. The backend already computes these.
4. Restore a concise route-evidence confidence explanation. The current score-component count is not scan coverage. Shared component names do not ensure equally complete evidence on both routes; scoring under uneven coverage warrants validation or stronger comparison rules.
5. Verify the latest APK on actual devices for GPS, motorbike/walk/future departures, native map scrolling and chosen-route handoff. Existing software tests and user screenshots do not collectively establish every final-build flow.
6. Verify active hosted limits and deployment revision. The status endpoint reports a hard-coded older buildVersion, so it is not a reliable Git commit identifier. A healthy status does not reveal remaining request allowance.
7. Standalone Google Geocoding integration is not implemented. Search selections resolve through Places and Android GPS addresses use the platform Geocoder. The PDF calls Geocoding potentially needed, so this is a literal setup difference, not a blocker for the current selection-based flow. Cloud API/key restriction settings were not inspected in this audit.

## Current operational evidence

Read-only `GET https://nightwise-f5fu.onrender.com/api/status` succeeded during this audit: ready=true, paused=false, searchEnabled=true, activityEnabled=true, scoringEnabled=true, budgetReady=true, Redis storage, both service radii 20 km, maxQueries=120, accessCodeRequired=true. No paid Routes/Places requests were made. This supersedes the earlier deployment-crash screenshot as a health observation, but does not certify which commit is serving or that the 10,000 Nearby allowance is applied.

Latest completed source checks before APK packaging: 200 unit tests, relevant narrow-phone browser regression, TypeScript and backend build passed. APK 2.0.7 passed signature continuity, version, asset consistency, hosted backend and server-secret-exclusion checks. Tests prove specified software behaviour; they do not validate the score as a measurement of street safety.

`research/area-hours-review-2026-09-14.md` records earlier live route and desk-research results. Its older deployment/paused statements are historical and must not be treated as current status. Recent user screenshots show successful populated live comparisons as well as allowance exhaustion; neither is a controlled multi-route acceptance study.

## Intentionally excluded, correctly

Community shop submission/voting, crowdsourced safety audits, live tracking/share links, internal turn-by-turn navigation, private-house activity measurement, street-light coverage, crime scoring and safety guarantees are not MVP omissions. The PDF defers or excludes them. Calling a route “safest” would contradict its wording guidance.

Overall: broader feature scope than the PDF, substantially implemented MVP, incomplete acceptance validation and a few remaining evidence/UI gaps. No defensible percentage or “10/10” reliability claim follows from the feature count.
